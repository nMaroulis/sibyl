# Exchange order discovery

Trade → Executions combines Sibyl submissions with **read-only imported orders**. Discovery reads existing exchange orders; it never places, cancels, replaces or retries an order. It works while new native execution is disabled. Demo discovery reads the actual virtual order tables and does not seed examples or advance the matcher.

## Provider coverage

| Client                    | Open orders                             | Recent history                                                                                                |
| ------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------- |

| Coinbase Advanced Trade   | Account-level Advanced Trade spot pages | Orders created in the selected range, in the key's permitted portfolio and `RETAIL_ADVANCED` placement source |

| Kraken                    | Account-wide orders without leverage    | Orders closed in the selected range, including older orders closed recently                                   |

| KuCoin Classic            | Account active-symbol snapshot, then paged spot orders | Up to 12 selected pairs. Native retention is up to two days for cancellations and seven days for fills. |
| Bitstamp                  | Account-wide open spot limit snapshot | Individual order and fill checks are available for imported orders. Recent account history discovery is pending. |

| Gate                      | Grouped open orders and paged recent finished cash spot orders | Recent windows filter on finish time. |

| HTX                       | Verified-wallet open order pages and recent orders for up to 12 selected pairs | History uses fixed 48-hour windows. API-cancelled orders are queryable for up to two hours. |
| MEXC                      | Account-wide open snapshot and recent orders for up to 12 selected pairs | Up to seven days. A saturated open snapshot or unsplittable history window reports a coverage limit. |
| Demo                      | Actual resting virtual orders           | Actual virtual orders created in the selected range                                                           |

The Trade sync form shows each account's coverage. Selecting only open-order accounts hides the recent-history control. Other providers remain unsupported for discovery. Authenticated venue acceptance is still pending. The adapter excludes unknown, delisted and unsupported markets and Kraken margin orders, and reports an exclusion count. A successful pass does **not** establish complete historical coverage or final settlement. Coinbase Simple Trade, other portfolios, derivatives and archived/delisted instruments are outside this contract.

## Durable scheduling

The user explicitly starts discovery for one active supported account, or all currently active supported accounts (at most 20). This selection is saved per account; subsequently connected accounts are not silently added. No account is activated by discovery.

The initial pass reads open orders, then a frozen recent window of 1, 3 or 7 days. One native page is read per worker tick. A completed enabled job starts another rolling pass about five minutes later. Individual order status/fill tracking is independent, so a discovered open order can still reach its terminal state after it disappears from an open snapshot.

SQLite stores each account's private cursor, stream, range, counters, configuration revision and next attempt. Orders, reconciliation scheduling and the page checkpoint commit in one transaction. Invalid evidence rolls back the page. Interrupted reads resume from the committed checkpoint. Configuration changes invalidate an older in-flight page; pause preserves an in-flight successful checkpoint without re-enabling the job. Inactive accounts wait; disconnected accounts stop and retain their evidence.

Five failed transient reads stop automatic discovery until an explicit resume. Provider admission/cooldowns preserve that failure budget. Authentication, malformed evidence and unsupported operations need attention immediately. Error messages are fixed and sanitized; opaque cursors never appear in API responses.

Each pass is bounded to 100 pages and 10,000 returned observations. Unpaginated Binance, Kraken, Bitstamp and Gemini open snapshots are limited to 1,000 orders. Binance recent requests use at most 24-hour windows; full 1,000-row windows are bisected until unambiguous, rather than skipping timestamp ties. A saturated one-millisecond window stops with a coverage limit. Coinbase uses native cursor/header pagination; Kraken uses native closed-order offsets/counts. OKX uses `after` with the oldest exact native order ID from each response and checks it moves backwards, including when all rows are excluded. Each OKX stream ends on an empty page. The native `begin`/`end` filter uses order creation time. Bybit uses separate realtime and history endpoints with opaque cursors and one fixed history window. The spot request uses the regular order filter and excludes margin, conditional and attached orders. Quote-sized market requests leave original base quantity and remaining size unknown. [Bybit realtime orders](https://bybit-exchange.github.io/docs/v5/order/open-order), [Bybit order history](https://bybit-exchange.github.io/docs/v5/order/order-list). These mutable exchange listings are observations, not transactionally consistent exchange snapshots. Repeat passes overlap the selected window to pick up changes.

KuCoin Classic reads a bounded snapshot of its active symbols, then resumes one market page at a time. Recent-order pages use the venue's `lastId` under the same saved pair and date filters. An unavailable active symbol is counted as an exclusion. An empty pair selection syncs open orders. Bitstamp retains its native original size when present and leaves cumulative fills unknown until separate order or execution observations arrive. [KuCoin active symbols](https://www.kucoin.com/en-au/docs-new/rest/spot-trading/orders/get-symbols-with-open-order), [KuCoin paginated open orders](https://www.kucoin.com/en-au/docs-new/rest/spot-trading/orders/get-open-orders-by-page), [KuCoin closed orders](https://www.kucoin.com/docs-new/rest/spot-trading/orders/get-closed-orders), [Bitstamp open orders](https://www.bitstamp.net/api/#tag/Orders/operation/GetAllOpenOrders).

Gemini reads one active-order snapshot and selects regular spot limit orders using the account’s market catalog. Gate flattens open-order groups under each pair’s page limit and uses separate finished-order pages with fixed second-based bounds. Bitget Classic requests `tpslType=normal` and advances `idLessThan` using the oldest native order ID on each page. Gate and Bitget recent passes cover the selected one-to-seven-day window. [Gemini active orders](https://developer.gemini.com/trading/rest-api/orders/list-active-orders) · [Gate spot API](https://www.gate.com/docs/developers/apiv4/en/spot/) · [Bitget Classic spot trading](https://www.bitget.com/docs/catalog/classic-spot-trade/classic-spot-trade).

MEXC checks the current open snapshot once. Use exact pairs for recent history. The spot `allOrders` endpoint has a 1,000-row cap and no continuation token. A capped response splits its frozen time window and persists both halves as a checkpoint. Sibyl keeps the last valid observations if a single millisecond still hits the cap. [MEXC open orders](https://www.mexc.com/api-docs/spot-v3/spot-account-trade/current-open-orders) · [MEXC order history](https://www.mexc.com/api-docs/spot-v3/spot-account-trade/all-orders).

HTX resolves one native spot wallet and rejects returned orders from another wallet. Open-order pages advance by the smallest native order ID. Recent discovery requires selected pairs and splits capped responses into smaller creation-time ranges within 48-hour windows. A capped single millisecond reports a coverage limit. Each pass keeps its wallet and pagination checkpoints across restart. [HTX open orders](https://huobiapi.github.io/docs/spot/v1/en/#get-all-open-orders) · [HTX historical orders](https://huobiapi.github.io/docs/spot/v1/en/#search-past-orders).

## Identity and execution evidence

Account ID, exact spot symbol and native order ID define a retained order. A native ID already attached to a Sibyl intent updates that row, preserving its reviewed request and origin. A client ID matching an uncertain Sibyl submission defers the discovered row to the existing [reviewed recovery](order-recovery.md) workflow; discovery does not adopt an identity on client ID alone.

New imported rows use a deterministic internal ID in `exchange_orders`, with `origin: imported` and `read_only: true`. Importing the same native order again updates it. Individual native fills use the existing shared [Account history identities](account-sync.md), so discovery itself never fabricates executions, duplicates fills or changes balances. The existing [execution dialog](order-reconciliation.md) links retained fills immediately and can import additional exact-order execution pages.

Missing quantities, creation times, prices and fees remain unknown. Quote-sized or conditional orders can be inspected with the original quantity and order instructions left unknown when the venue does not report them in those units. An OKX quote-sized market request does not supply a native executed quote total. The execution dialog shows the cost from retained fills. Imported amount/price amendments update the read-only observation; older cumulative fills or reopened terminal observations are rejected. Amendments to reviewed Sibyl intents require separate handling and are not silently substituted for the reviewed request. An absent order never implies cancellation. Fees/settlement, execution busts and general amendment reconciliation remain incomplete.

Both UI controls and backend services reject submission/cancellation of imported rows. Status and execution checks remain read-only, including manual checks of saved inactive accounts. Pause discovery stops future discovery pages; pause tracking stops that order's status reads. Neither action cancels a native order.

## HTTP contract

All paths use `/api/v1`. Read responses have `Cache-Control: no-store`.

| Method | Path                                            | Effect                                                                                                                                                      |
| ------ | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/exchange-orders/monitor`                      | Paginated local/imported monitor; filters `account_id`, `exchange`, `origin` (`sibyl`/`imported`), `status` (`active`/`terminal`), `limit` (1–50), `offset` |
| GET    | `/exchange-orders/discovery`                    | Local supported-account metadata and public progress; no provider reads                                                                                     |
| POST   | `/exchange-orders/discovery`                    | Start/resume with `account_id` (blank: active supported accounts), `days` (1–7), `symbols` (up to 12 exact history pairs for Binance, KuCoin, MEXC or HTX)                                 |
| POST   | `/exchange-orders/discovery/{account_id}/pause` | Persist a discovery pause                                                                                                                                   |
| POST   | `/exchange-orders/{id}/refresh`                 | Observe native status and one execution page, including imported rows                                                                                       |
| GET    | `/exchange-orders/{id}/reconciliation`          | Inspect retained order/fill evidence without provider reads                                                                                                 |

The existing `GET /exchange-orders` and trading report retain their latest-100 **Sibyl submission** contract; imported observations appear in the combined monitor and their executions in Account history. Monitor filters are applied before pagination. Combined views include separately labeled production, test, Demo and retained inactive/disconnected records; they do not sum their funds.
